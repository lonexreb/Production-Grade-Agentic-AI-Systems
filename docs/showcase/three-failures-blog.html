OpenAgentOS · real reported failures · runnable proofs

Your AI agent charged a customer twice. It's not the model's fault.

Three failures real developers reported publicly — reproduced as runnable code first (the bug, with numbers), then fixed with boring runtime primitives (the proof, with numbers). The terminal recordings below are the actual scenarios running; both halves execute in CI on every push.

01

The side effect that ran twice

Reported on the LangChain forum and dissected in a widely shared write-up: LangGraph's interrupt() works by re-running the node it was called from. Any side effect placed before the interrupt executes again when the human answers — duplicate records, double writes.

The bug, reproduced 2 rowsone approved action, naive node
The fix, proven 1 rowgate-first + idempotency ledger
The primitiveinterrupt() is the FIRST statement of the gated node, and the effect sits behind an execute_once key — a re-run replays the stored result instead of executing.
02

The retry that charged twice

An r/AI_Agents developer's fulfillment agent double-triggered a Printify order when the confirmation arrived during a retry window. The canonical variant is the Stripe-timeout double-charge: the charge commits server-side, the response is lost, the retry pays again. Reliable test networks hide it; production networks don't.

The bug, reproduced 2 chargesone order, naive retry
The fix, proven 1 chargedeterministic key, provider dedupes
The primitiveThe runtime's side-effect key (run_id:node:scope — stable across retries by construction) is forwarded to the provider as its idempotency key. The retry still fires; the provider dedupes it.
03

Crashed at item 37, restarted at item 1

The pattern across dev.to and engineering blogs: an agent researching 50 companies makes it through 37, the server restarts — and it starts over from company 1, re-spending real API money on work it already did. State lived in process memory; the process died; the state died with it.

The bug, reproduced $10.80 re-spent36 items redone from memory-only state
The fix, proven $0.00 re-spentfresh process resumes at item 37
The primitiveOne item per graph superstep means one checkpoint per item — for free. Nobody wrote checkpointing code; durability is a property of the runtime, not a feature you remember to add.

The common thread: none of these are model problems, and none of the fixes are clever. Idempotency ledgers, durable pauses, checkpoint-per-step — mechanical primitives, applied by a runtime so every agent gets them without remembering to.
